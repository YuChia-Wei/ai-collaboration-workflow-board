# 產品原生待辦項目與操作

2026-11-25。本規格定義使用者在未設定外部來源的私有產品中，如何從空清單開始建立、排列、修訂和關聯工作。規格包含產品待辦的行為與項目的不變量，適用於所有保存或操作這些資料的入口。領域設計說明了規則來源與取捨，HTTP 契約定義欄位與相容行為。[原生 Scrum 待辦設計](../../../design/product-evolution/native-scrum-backlog.md) · [Portfolio v1](../../../../src/Contracts/PortfolioV1/README.md)

## 識別、範圍與型別

1. 一個可見產品對應一個 Board project。該 owner／store／project 內的原生 backlog 可隨建立項目開始使用，初始修訂為 0、項目為空。讀取依 read 能力，寫入另需 plan 及可寫 project。伺服器從已驗證身分解析 owner，所有引用都在這個產品內解析。
2. 原生項目的識別由來源 native 和產品內穩定的 item ID 構成。標題可同名，改名、排序或重開保留識別。外部觀察則由來源 repository 和 Issue 識別。顯示名、數字和相似文字不足以合併兩張卡。
3. 每張卡必有類型、標題、開關狀態及可供 workflow 選取的來源版本，說明可留白。建立後的型別與父項固定。每種項目只適用下表中的關係。

| 類型 | 必要父項 | 可有的子項 | 該類型的附加資料 |
| --- | --- | --- | --- |
| Epic | 根層 | Feature | 一項產品成果 |
| Feature | 同產品原生 Epic | User Story | 為達成成果提供的能力 |
| User Story | 同產品原生 Feature | Task | 使用者需要的結果 |
| Task | 同產品原生 User Story | 無 | 支援該結果的工作 |
| Bug | 根層 | 無 | 必填預期、實際行為。可連一張同產品原生 User Story |

最後一欄的成果、能力、結果與工作由標題與說明表達。Bug 的兩項行為與可選 Story 有專用欄位。Bug 的 Story 關聯可建立、改指或解除，均保留 Bug 在根層的位置。上述五種項目都可獨立於任何 workflow 存在。

## 建立、修訂與順序

open／closed 是供既有讀者使用的狀態分類。新卡採用各類型配置的詳細工作狀態，以明確轉換關閉或重開。僅有舊分類的項目可明確對應到流程。完整規則見[生命週期、交付與部署規格](lifecycle-and-delivery.spec.md)。

| 意圖 | 成功後可觀察的事實 | 拒絕或競爭的例子 |
| --- | --- | --- |
| 建立項目 | 同產品內出現一張處於該類型初始階段的卡，放在根層或指定父項直屬清單的末端。 | 識別已使用、標題空白、缺父項、錯誤父型別或 Bug 的預期／實際行為缺漏。 |
| 修訂或關閉／重開 | 修訂所選項目的文字及適用的 Bug 資料。按詳細流程轉換該卡，既有粗分類卡也可沿用原開關操作。保留識別與同層位置。 | 企圖更改型別或父項、使用其他產品的 Story，或以過時的待辦修訂覆寫。 |
| 移動位置 | 把選定項目放到同層另一項之前，或移到同層末端。原同層中其餘項目的相對順序保留。子孫仍屬於原有父項。 | 目標來自其他父層或產品。跨父項搬移沒有合法的同層目標。 |
| 讀取 | 另一個工作階段可讀到相同內容、版本與各組相對順序。關閉的父、子仍可區別。 | 沒有當前產品的存取權時，其他產品的內容不應出現在回應。 |

查詢傳回產品 backlog 的修訂與項目。三項寫入均使用剛讀到的 backlog 修訂。同一修訂下發生競爭時，過時的操作會被拒絕，已接受的內容仍完整。已提交但遺失回應時，使用原操作識別、內容與修訂重送。授權仍須有效。關閉或重開限於選定項目，父子、相關 Bug 及關聯 workflow 各自維持原狀。更新順序也不會把卡排進 Sprint。

## 產品的 Sprint 規劃

使用者可在未串接外部系統的產品管理自己的 Sprint 行事曆。產品建立時的節奏為兩個整週、星期一開始，可設定為 1 至 4 個整週以及星期一到星期日的任一天。即使尚未建立任何一期，也能先建立工作項目。查詢需有本產品的 read，設定節奏、建立期間和配卡需有 read、plan 及可寫的 project。[Scrum 與 iteration 的設計依據](../../../design/product-evolution/native-scrum-backlog.md#sprint-節奏與工作歸屬)

| 行為 | 可觀察的規則 |
| --- | --- |
| 設定產品節奏 | 保存此產品之後建立 Sprint 時採用的週數與起始星期。沿用既有 Sprint 的識別、名稱及日期。 |
| 建立具名 Sprint | 指定產品內的穩定識別、非空名稱及符合起始星期的開始日。結束日為開始日加上「7 × 週數 − 1」個日曆日，起訖皆含。各期按開始日排序，可跨月或年度。 |
| 驗證期間 | 開始日須為有效的日曆日。若新期間包含另一期間的任何一天或識別已使用，拒絕建立。允許相鄰或中間有空白日期。同一日期可由不同產品各自規劃。 |
| 將項目排入、改排或移出 | 建立或編輯這張卡時指定同產品既有 Sprint，或明確清空。每張卡只有一個目前所屬 Sprint，可維持未排期。新卡、舊列與父子項都沒有自動分派。 |
| 並行與回讀 | 節奏、建立期間及配卡共用產品 backlog 修訂，沿用相同回條重送與權限。送出過時修訂時回報衝突，重新讀回產品即可取得最新設定、期間與各卡選擇。 |

以跨年度排程為例，採預設節奏建立「年末整理」，2026-12-28（週一）開始，結束為 2027-01-10（週日）。之後改成一週、週三開始，此期仍是原日期。若再以 2027-01-06 建一期會重疊，應被拒絕。以 2027-01-13（週三）建立則可成功，結束為 2027-01-19（週二）。

另一項驗收可從既有未排期的 User Story 建立一個子 Task。將 Task 排入「年末整理」後，另一個 session 查回同一產品，Task 有該 Sprint，Story 維持未排期。以舊版編輯要求修訂 Task 說明時，省略 Sprint 欄位會保留排期。明確移出才清空。兩次操作皆保留 Task 的工作階段及其 workflow 關聯。

## 關聯工作流程

workflow 可從零、一個或多個項目開始規劃，再補連或解除。對原生卡，建立或補連須能在本產品找到該項目及使用者選取的版本。服務保存當時的來源、識別、版本及選取快照。其他 session 既能讀取產品待辦目前的標題，也能在工作關聯與歷史讀到當時的選擇。解除關聯針對 workflow 先前保存的選取版本。外部來源在 catalog 被移除或原生卡後來改名時，此規則仍適用。[既有工作關聯與命令契約](../../../../src/Contracts/PortfolioV1/README.md)

workflow 規劃並記錄實作，Scrum 卡組織產品工作。同一個 workflow 可同時支援一張 User Story 與一張 Bug。由兩張卡前往的仍是同一份工作。即使原生 Task 連到有執行中 task 的 workflow，兩者仍各自保有當前狀態、授權與歷史。

## 可觀察的驗收情境

以下是從正常的 Scrum Board 與 Workflow Board 入口應能查驗的結果。

| 情境 | 操作與預期結果 |
| --- | --- |
| 無外部來源的第一張卡 | 在虛構產品「稻禾預約」直接回報 Bug「週日顯示為可預約」，預期週日停診、實際可選取週日。未指定 Story、外部帳號或 workflow 即可送出。重開該產品能看到同一張根層 Bug。 |
| 持續細化與排序 | 建立 Epic「線上預約」、Feature「挑選時段」、User Story「看到可約時段」及 Task「列出週末邊界」。把 Bug 移到 Epic 前，將該 Story 設為受影響項目。第二個 session 能讀回新順序、四層結構與 Bug 關聯。 |
| 無效結構 | 試圖在 Epic 直下建 Task、以 Task 當成 Bug 的受影響 Story，或把 Feature 移到根層 Bug 之前。回讀的樹與同層順序維持最後一次成功的結果。 |
| 跨產品與舊版本 | 另一產品即使有同名 Epic 與 Task，也看不到「稻禾預約」的工作。兩個 session 同讀一版，第一個成功改標題，第二個用舊版移動。第二個收到衝突，重新讀到第一個的標題。重播第一個成功操作只得到原結果。 |
| 獨立的關閉與重開 | 仍有 open 子項時關閉 Epic，子項維持 open。關閉或重開 Bug，受影響 Story 與 workflow 的狀態均維持原值。 |
| 跨看板接手 | 同一 workflow 連到原生 Bug、Story 及既有外部卡。由三張卡查到相同 workflow。後來編輯 Bug 標題，工作仍保有選取時的 Bug 快照。從 workflow 解除舊選取後，現行關聯消失，歷史仍得以查回。 |
| 來源替換 | 外部 catalog 先讀到一張卡，再回報過期或更新為空。可從原生待辦讀到先前的樹及 Bug。外部區域呈現該次觀察的涵蓋狀態。 |

本機有兩個可重現的驗證入口。執行 `npm run test:portfolio`，由 HTTP 命令送入真實應用邏輯與套用 migration 的記憶體 SQLite，再從查詢端核對階層、權限、衝突、操作重送、外部來源替換與 workflow 快照。執行 `npm run build` 後再執行 `npm run test:portfolio-browser`，由第一個瀏覽器工作階段從空產品建立入口回報 Bug、拆分四層工作、排序與連結，再由第二個工作階段重新讀回。線上 Sites 與 D1 的部署驗收另依當次版本查核。[HTTP 與儲存測試](../../../../src/Tests/portfolio-native.mjs) · [瀏覽器情境](../../../../src/Tests/portfolio-native-browser.mjs)
