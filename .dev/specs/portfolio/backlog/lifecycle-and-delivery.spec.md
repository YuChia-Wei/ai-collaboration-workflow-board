# 原生 PBI 的生命週期、交付及部署追溯

2026-11-25。產品負責人選定按工作類型管理進度、按受領對象登記交付、按環境追查實際版本。本文定義這三種事實各自的責任、讀寫條件與驗收結果。範圍為既有 owner／store 內的私人 Board project 和原生 PBI。[產品決策與情境](../../../design/product-evolution/pbi-lifecycle-and-delivery.md) · [原生項目規格](native-backlog.spec.md) · [Portfolio HTTP v1](../../../../src/Contracts/PortfolioV1/README.md)

## 工作狀態

產品為五種項目提供初始流程。帶 read 的身分可讀取項目及流程，有 read、plan 且可寫此產品的身分可建立、轉換或配置。箭頭為允許的前進操作，表內另外列出退回或重開。新項目使用建立當下該類型設定的初始狀態。

| 類型 | 預設路徑 | 其他轉換與含義 |
| --- | --- | --- |
| Epic | New → Active → Done | Done 可重開至 Active。結束與否由此 Epic 的成果範圍判斷。 |
| Feature | New → Active → Validating → Done | Validating 退回 Active，Done 可重開至 Active。部分 Story 交付後，Feature 仍可 Active。 |
| User Story | New → Active → Testing → Done | Testing 未通過可回 Active，Done 可重開至 Active。Done 表達團隊對該 Story 工作完成的判定。 |
| Task | New → Active → Done | Done 可重開至 Active。一項文件 Task 即使無部署對象也可以完成。 |
| Bug | New → Triaged → Active → Retesting → Done | Retesting 未通過可回 Active，Done 可重開至 Active。預設另允許分流階段以重複或不修的明確理由結案。 |

工作階段有穩定識別、顯示名及 open／closed 分類。項目上的 status 是該階段的分類，供跨類型清單及既有讀取者使用。具體階段只能經允許的轉換推進。舊版編輯仍可改文字，嘗試繞過流程直接改變已採用新流程項目的開關狀態時，服務回報衝突。

Bug 分流後若判定重複，應提供原因及指向同產品另一張確實存在的 Bug。決定不修時也應說明原因。兩種處置可結束該 Bug 的工作，均不產生修正、部署、交付或收件人驗收的證據。轉換保留當時的狀態識別與標籤、實際操作者、時間及相關處置。改名後仍能解讀較早的紀錄。父子卡、受影響 Story、所連 workflow 的狀態各自演進。

可替單一產品的單一類型選擇初始階段、添加階段、重新命名或調整允許的轉換。所有階段須可從初始 open 階段抵達，且各有路徑到至少一個 closed 階段。每個 closed 階段都能直接重開至至少一個 open 階段。仍有卡使用的階段要保留其識別及開關分類。可先把相關工作逐筆移出，再調整流程。其他產品和其他類型各自保有原有設定。

## 既有 open／closed 項目

只有 open／closed 的既有資料，以原分類和「尚未對應詳細階段」讀回。讀取舊的 closed 不會生成 Testing、Done、交付或部署紀錄。舊列可繼續沿用原開關操作，也可明確對應至同分類的有效階段。從對應之後開始，依詳細流程執行下一次轉換。既有 workflow 保存的關聯快照仍指向選取當時的版本。

## 交付、部署嘗試與環境讀回

| 事實 | 建立時需要的資料 | 讀取時所能回答的問題 |
| --- | --- | --- |
| 產品交付政策 | 預選的主要環境、受領對象與交付證據類別。環境可先不選，受領對象也可逐次指定。 | 目前預設應交給誰，要以何種證據登記交付。 |
| 交付草案 | 識別、產物、對象與範圍。範圍指向本產品 PBI，逐項寫出包含的成果或延期原因，至少有一項本次包含的成果。 | 這次預計交付哪些結果，哪些仍待後續。 |
| 實際交付 | 選定草案、確切產物、受領對象、滿足政策要求的證據類別、證據與發生時間。 | 哪個對象收到了哪個產物及哪部分成果。既有紀錄保留當時適用的政策、版本及範圍，供日後查回。 |
| 環境與適用性 | 環境以產品內穩定識別管理，可命名及停用。項目可明示部署不適用。 | 可針對各個客戶的 UAT 分開查閱。文件或研究 Task 可說明「部署不適用」。 |
| 部署嘗試 | 環境、確切產物、本次範圍、時間、結果及依據。重試與回復各有自己的識別，關聯先前嘗試。 | 這項工作在哪裡嘗試部署哪個版本，結果如何，後續曾重試或回復哪一筆。 |
| 環境讀回 | 確切環境、當時觀察到的產物、觀察時間、證據及觀察識別。 | 此環境最後一次有依據的生效版本與時間。沒有讀回時，實際生效版本為未知。 |

Board 提供登錄介面供獲授權的規劃者保存證據。記錄成功的嘗試與在該環境確認生效的版本是兩件可分別發生的事。QA 上的版本不能代表客戶 A 的 UAT，同類型的兩個 UAT 也各自有自己的識別。登錄交付只對當時紀錄的受領對象成立。這些命令均為保存紀錄，不執行任意 pipeline、觸發遠端部署或授予可信人類簽核。[交付與部署 Issue 的責任範圍](https://github.com/YuChia-Wei/ai-collaboration-workflow-board/issues/8)

卡片在指定對象下顯示整項 Delivered，需要一筆確認交付直接包含該卡，且範圍明列全項。部分成果或該卡的子項已交付時，畫面應顯示交付的內容、尚待交付或延期的部分。查某一環境的 Deployed 時，須能連到包含該 PBI 的成功嘗試，且環境讀回指向同一產物。已有較新部署嘗試而尚無新的讀回時，保留最後確認版本與時間，提示當下未知。對部署不適用的項目，舊紀錄仍可追查。

交付與部署範圍中的項目須同屬此產品，每張卡限一次。範圍保存卡的標題、來源版本及包含或延期的具體成果。重試引用同一環境同一產物的失敗嘗試，回復引用同一環境先前成功的嘗試並填另一確切目標。歷史依發生或觀察時間解讀，讓較晚送達的舊讀回保留在正確時間點。

回復範圍表達哪些工作受到這次回復影響。重試會繼承前次嘗試的用途，重試失敗的回復仍屬於回復。若要判讀工作是否已在復原版本生效，需有同一環境中該復原版本正常部署成功、範圍包含這張卡，以及觀察到該版本的證據。把修正連到回復紀錄，只能證明它受到此次操作影響。

## 一致性與驗收

生命週期配置與工作項目共用產品待辦修訂，以便在選擇階段到送出轉換之間察覺設定變更。交付、環境及讀回使用獨立的交付修訂。同一預期修訂只接受能在當前版本完成的寫入。保留原操作識別及 payload 可恢復含糊的回覆，重送仍需授權。對舊卡的對應、流程規則、卡的狀態、交付事實與環境觀察應能在新的 session 重新讀回。

| 情境 | 從另一個工作階段應能讀到的結果 |
| --- | --- |
| Bug 重驗退件 | 由 New 經分流、修正進到 Retesting，記下退回後再修正、重驗並完成。歷史包含每次往返。直接跳過分流或重驗會被預設流程拒絕。 |
| 分流結案 | 指定同產品另一張原單及原因後可記為重複。原單仍保留其狀態，這張 Bug 可查出為何結案。若只填自己或缺少原因，原 Bug 維持原狀。 |
| 改流程或採用舊資料 | 團隊改名、加入 Review 與對應轉換後，新操作採新設定。較早紀錄仍有原標籤。舊 closed 卡在明確對應前只顯示其既有分類。 |
| 部分交付 | 某 Feature 有兩項可獨立交付的成果。對客戶 A 的草案列出其中一項包含、另一項延期及原因。確認交付時保存版本與受領依據，Feature 可維持 Active。 |
| 跨環境失敗／回復 | 相同版本在 QA、客戶 A 的 UAT 均有各自的部署與讀回。Production 嘗試失敗時仍顯示先前確認的版本及時間。重試有獨立紀錄，實際生效版本依新觀察更新。後來回復也保有前一版本及其相關嘗試。 |
| 權限、競爭與重送 | read 身分可查閱，寫入需 read 與 plan。舊修訂的操作收到衝突，按原樣重送已成功的請求只交回原結果，同一操作識別換資料則被拒絕。 |

此表描述預期行為。核心與儲存驗證、瀏覽器操作、部署後服務讀回及使用者親自試用各自需要對應證據。
