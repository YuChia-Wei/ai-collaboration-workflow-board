# 產品範圍與責任

日期：2026-10-22。狀態：初期設計；整體方向已接受，細部選型依 [待決事項](decisions-and-questions.md) 收斂。

## 產品目的與使用者

Workflow Board 的核心價值是讓人類與外部 AI Agent 圍繞同一份工作事實協作：規劃工作、拆分任務、讀取精確文件版本、記錄進度與證據、提出需要決定的事項，以及跨對話接手。Board 原先是線上工作紀錄與工作／專案管理產品；未來桌面包裝與執行整合服務這個目的。

主要使用者包括決定需求與接受成果的專案 owner、執行或接手工作的 Agent，以及需要檢視來源與交付狀態的團隊成員。目前已驗收入口仍是單 owner 的有限情境，團隊身分與權限不能由願景推定存在。

「ADE（Agentic Development Environment）」可作討論中的方向名稱，尚未定為正式產品名，也不等於首版要重建 IDE。能力優先順序如下：

1. **協作與接手**：先讓現有 Agent 工具可靠使用 Board，完成工作、文件、審閱、授權與人類決定的完整旅程。
2. **執行整合**：之後才考慮啟動、停止、觀察與管理 Agent，並定義程序、憑證、工具與工作區的控制邊界。
3. **完整 IDE 體驗**：編輯器、終端、除錯等深度整合是可選遠期方向，沒有承諾必要性或日期。

## 責任分工

| 能力／資料 | 主要 owner | 邊界 |
| --- | --- | --- |
| Workflow、Task、Assignment、文件 revision、operation receipt、可信授權及 UI | Board | 保存其工作事實，提供 API／CLI／MCP／UI；平台通行不等於業務權限 |
| ADR、Lesson、Workflow 的通用紀錄方法與生命周期 | Framework | 沿用各紀錄語意；決策、觀察、接受及規則採納不能混為一談 |
| 記憶選取、摘要、形成、引用、失效與按需召回契約 | Framework 規劃主責 | 對不同專案與工具可用，不把 Board 或雲端設為必要條件 |
| 需求、決策內容、知識適用範圍、來源授權與保留政策 | 各專案 owner | Framework 提供方法，不能代替專案作決定 |
| Session 事件、上下文注入及使用觀察 | 實際 Agent client／runtime adapter | 必須接到該工具真的提供的事件與入口；有 MCP 工具不代表自動載入 |
| 記憶來源查看、版本追溯與人類操作介面 | Board 與 Framework 整合 | Board 可成為來源及介面，沿用所選契約，不建立另一套通用記憶權威 |
| 程序執行、隔離、停止、資源控制 | 未來執行整合能力 | 待明確需求後決定落點，不預設先建立另一個 repository |
| 開發工作狀態、排程與優先順序 | 各自 GitHub Issues／Projects | 本設計不取代現行工作管理，也不擅自搬遷 Framework 的治理資料 |

單一領域核心指的是**同一 bounded context 的業務規則與應用案例可被多種 adapter 使用**，不表示把 Board 與 Framework 合併成一個大型 domain，或讓前端承擔可信授權及交易不變量。

## Board 範圍

### 近期目標

- 保留已交付的可攜核心、線上 MCP／API、Windows CLI 與跨介面接手。
- 補足可靠性及完整退出能力的證據與缺口（#6），沿用既有 CAS／receipt 機制。
- 收斂可信人類入口（#14）與後端提交／審核／成果接受規則（#13），接續 #7 已完成的 UI。
- 按需求安排不同 Agent 的獨立身分（#11）、有來源的 session 觀察（#12）及交付／部署追溯（#8）。

這些工作讓產品能清楚回答「誰基於哪個版本做了什麼、哪些工作完成、哪些成果已接受、哪些資訊仍未知」。任務完成、成果接受與 Agent 程序停止必須分開呈現。

### 後續部署目標

| 情境 | 期望價值 | 資料權威與階段 |
| --- | --- | --- |
| 現有 Sites 網站 | 持續交付與驗證協作流程 | 現行 JavaScript／Worker／D1；近期主線 |
| 團隊自管服務＋網頁或桌面 client | 容器、部署與維護可由團隊掌握 | 線上服務為權威；服務端及 PostgreSQL 遷移需另評估 |
| 桌面 client 連線上服務 | 提供桌面工作入口及日後本機整合 | 桌面包裝本身不構成離線系統 |
| 單機本地離線產品 | 銀行、敏感或外網受限環境可保存及接手工作 | 本機 SQLite 為所選權威；完整本地產品開發依進度延後 |
| 企業內網服務＋clients | 無外網但有內網的多人協作 | 中央內網服務為權威；與單機離線是不同部署情境 |

「前後端分離」先要求契約及責任分離，不強迫第一天就以不同網域、服務或 repository 部署。選定一份 workflow 的可寫權威後，不因斷線默默雙寫、切換 store 或啟動雙向同步。

## 技術方向

- 未來後端語言以 **C#／.NET 優先**，理由是 owner 熟悉、容易 review 與長期維護。Rust 為有興趣學習的次選；Go 為第三順位。這是選型偏好，不是已授權重寫。
- 初期 Sites 保留目前技術。現有 JavaScript 核心能否暫時重用、何時建立 C# 實作，依移出 Sites 的切片決定。
- 遵循 DDD、Clean Architecture／Hexagonal Architecture；要求領域語言、不變量、port 及可觀察行為，不能只以資料夾結構驗收。
- 本機 SQLite 方向已接受。未來離開 Sites 的伺服器資料庫優先評估 PostgreSQL；目前 D1 繼續使用。
- UI 框架與桌面外殼未選定。Tauri、WinUI／WebView2 與 Electron 的比較見 [架構](architecture-and-deployment.md)；macOS／Linux 是否首批支援仍未決。

## 首階段範圍外

首階段不包含全功能 IDE、任意 Agent 的自動啟停、跨裝置雙向同步、跨專案個人記憶、模型訓練或把私人聊天自動匯入工作資料。也沒有因本次規劃而部署新的服務、安裝記憶工具或變更既有資料保留政策。

記憶可以在完整 Agent 執行管理之前提供價值；但必須先確立來源、有效性與取用契約，不能以接上向量資料庫代表「AI 已經學會專案」。
