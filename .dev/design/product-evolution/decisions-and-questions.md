## 演進選型的待決

| 議題 | 保留選項 | 何時需要決定 |
| --- | --- | --- |
| 移出 Sites 的第一個切片 | 自管服務、替代 persistence、或先限定新 host | 確定實際部署需求時；不為語言偏好立即全重寫 |
| 目標平台與 UI | Windows WinUI／WebView2、Tauri、Electron、維持網頁 | 桌面切片開始前；先確認 macOS／Linux 是否首批需求 |
| 本機 host | 內嵌、sidecar、使用者層級背景服務或系統服務 | 正式本地產品開始前，連同身分、生命週期與更新考量 |
| 本地 AI | 先無 AI、企業模型端點、完全本地模型／embedding | 根據環境網路與資料政策；不能由 SQLite 自動推定 |
| 同步 | 暫不提供；或未來另設衝突／權威轉移契約 | 同一工作確有多節點離線寫入需求時 |
| Agent 執行管理 | OS process／受控 runner／容器等 | 協作旅程成熟且有明確執行需求後 |
| 記憶接入 | 現有查詢、全文／向量／圖索引、候選 library／service | Framework 提案收斂最小召回契約及品質基準後 |

## Framework 記憶待決

1. 方法應放在現有能力或新 capability；不能先假設需要新 skill。
2. 召回單位、相關性、來源效力與輸出預算；什麼缺口值得增加索引。
3. 第一個 client／事件及可觀察的載入、引用或使用結果。
4. 摘要、索引與原文的存放、版本、失效、保留及刪除政策。
5. 自動形成候選的範圍，以及沿用哪個既有專案寫入政策。
6. 與 #481／#483 的專案身分、資料 owner、provider 操作如何銜接；Board adapter 保持可選。

遇到尚未決定的項目，應先完成不受影響的盤點及設計，再針對會改變下一個交付的具體選項收斂。已接受方向與既有授權持續有效，不因換文件、換 session 或形成候選就重新建立一輪核准程序。
