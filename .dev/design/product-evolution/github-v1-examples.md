# GitHub 第一版的行為範例與驗收

**01、02 已有實際 Web 入口。** 在儲存庫根目錄執行 `npm run build` 及 `npm run preview:portfolio`，開啟終端顯示的網址。首頁、Scrum Board、Workflow 執行看板與雙向 PBI 關聯走本機組建的 Worker，兩個瀏覽器工作階段共享同一個隔離測試資料庫。[本機試用方式](../../../README.md#試用產品總覽與兩種看板) · [跨 session 的瀏覽器驗收](../../../src/Tests/portfolio-browser.mjs)

從[離線互動樣稿](github-v1-demo.html)選「澄河」，打開「#11 列出可預約時段」，進入「WF-31 整理時段資料」。點它關聯的另一張 PBI，就能看到同一份工作如何支援兩項需求。首頁也能直接開啟一筆沒有 PBI 的調查並補連。重設示例或重新載入即可重新開始。

第一輪請用三個問題觀察畫面。不必先知道專案名稱，能否找到待處理的工作？從任一張卡能否看出哪個 workflow 在推進這項需求、下一個人該接哪一步？如果只有一項成果通過驗收，畫面能否解釋這次可交付哪些項目、哪些要等？後續產品切片沿用相同的可觀察結果。[範圍](product-scope.md) · [PBI 與實作順序](board-roadmap.md)

## 情境資料從哪裡來

| 參考的作業型態 | 全新編寫的例子 | 要驗證的差異 |
| --- | --- | --- |
| AICF 型，有 GitHub Project，透過階層、迭代及自訂欄位規劃工作 | **澄河**，虛構的場地預約產品。#11 列出可預約時段、#12 匯出預約明細、#13 顯示場地說明。第 1 天 WF-31 推進 #11 和 #12，WF-32 調查時區，尚未掛卡 | 共用工作如何計數、規劃狀態如何與實作進度並存、工作從一張卡接回另一張卡 |
| ArchPrecept 型，從 repository Issues 開始，能逐步拆工作並分批交付 | **石庭**，虛構的範例目錄產品。#11 產生範例目錄，沒有 Project，初始沒有 workflow。延伸的整合資料另設一張原生子 Issue 和一項只寫在正文的工作構想 | 相同 Issue 號如何隔離、缺少規劃欄位仍能工作、正文中的構想如何避免被誤認為已建立的子 Issue |

所有標題、內容、來源識別、關聯與事件由測試自行定義。規劃時可以閱讀三個實際產品的工作現況；展示、開發整合、E2E 和 CI 都不讀取或寫入 AICF、ArchPrecept 或 Workflow Board 的實際 repository、工作資料庫、Issues 或 Projects。也不用它們的程式碼、匯出檔、真實回應、工作紀錄或憑證建立 fixture。被測的 Board 版本由獨立測試實例執行，實例只載入情境指定的資料。

**兩種作業方式如何評估。** 對已有 Project 的團隊，測試重點是沿用其規劃語言。產品負責人可把兩張卡排進同一迭代，協作者只開一份共用工作，在交接中說明各卡還缺哪項證據。對從 Issues 起步的團隊，建議保留 Feature 作為目標，只把需要單獨驗收或分批交付的成果拆成子 Issue。以石庭為例，假設「產生範例目錄」底下有可獨立使用的目錄輸出，以及依賴新版輸出的使用說明。Agent 可先交接輸出結果；負責人依相容性表決定能否先發輸出。此作業方式可在沒有 Project、沒有固定 Sprint 的情況下評估，日後要採用時再由各產品決定是否調整工作習慣。

## 從首頁到工作交接

### 例 1．兩張卡共用一份工作

- **前提**：第 1 天澄河有兩筆進行中的工作。WF-31 的工作單連到 #11、#12，更新時間 09:20。孤立的 WF-32 更新時間 10:05，待決事項是預約頁顯示時區。石庭已讀取完成，沒有進行中的工作。
- **操作**：先從首頁打開 WF-32，再由澄河的 Scrum Board 分別從 #11、#12 開啟 WF-31。也可以由產品入口直接進入 Workflow 執行看板。
- **結果**：首頁有兩個產品，進行中清單恰有 WF-31、WF-32 各一筆。從兩張卡到達的 WF-31 顯示同一份證據和交接「核對兩組時段的起訖時間」，可循任一關聯回到正確卡片。WF-32 顯示待決與觀察時間，從首頁就能接手。

### 例 2．先調查，後來才知道屬於哪張卡

- **前提**：WF-32 建立時沒有選取 PBI。
- **操作**：從 WF-32 補連澄河 #11，再由 #11 回查。產品切片另用一個全新 session 接手，然後解除這筆關聯。
- **結果**：補連後 #11 恰有 WF-31、WF-32，#12 仍只有 WF-31；WF-32 的時區證據與下一步仍在。產品切片應在新 session 讀到同一狀態，解除後兩邊都移除目前關聯，歷史可讀到「建立時無 PBI → 補連 #11 → 解除 #11」。另一個建立案例一次選 #11、#12，兩張卡應讀到同一個新 workflow，並可查回建立當時各自選取的來源版本。
- **樣稿覆蓋**：目前能操作補連與雙向回查。同頁狀態供反覆演練；建立、解除、歷史及跨 session 保存由第一個產品切片驗收。

### 例 3．兩個產品都有 #11，只有一個使用 Project

- **前提**：澄河和石庭屬於不同 Board 專案與不同合成 repository，兩邊都有 #11。
- **操作**：補連澄河 #11，再開啟石庭 #11 和石庭的執行看板。
- **結果**：石庭顯示「產生範例目錄」，關聯工作為空，畫面不會出現澄河的迭代、狀態或 WF-32。只有 Issues 的產品也能依 Roadmap 02 建立、補連工作。測試以 repository 識別及來源 Issue 識別比對，顯示編號只用來方便人閱讀。
- **錯誤變體（產品切片）**：來源只回第一頁並在下一頁斷線時，要顯示取得範圍。已有快照可顯示上次成功時間；首次讀取失敗則顯示未知。兩者都與石庭「已讀取、零筆」有可見差別。

## 透過 GitHub 管理 PBI

### 例 4．從 Scrum Board 編輯，再由來源重新讀回

- **前提**：受控來源內澄河 #13 為 open，Project 狀態為「待辦」，可選「待辦／進行中」。石庭只使用 Issues，其原生子 Issue 有獨立識別。
- **操作**：由 UI 把澄河 #13 改名為「顯示無障礙場地說明」，關閉再重開 Issue；另將該 Project item 改為「進行中」，調到 #11 之前。以全新讀取重開 Scrum Board，展開石庭的子項。
- **結果**：來源能讀回新標題、open、Project 狀態與 #13 在 #11 前的順序。關閉期間仍能看到當時的 Project 狀態，各次操作均未改變 workflow。石庭只展開真正的子 Issue，正文裡的工作構想仍為正文。
- **失敗變體**：發出編輯前來源已換版，顯示最新版本與尚未送出的文字；來源拒絕寫入則保留輸入並標明拒絕的動作。以受控來源的最後內容和實際收到的請求核對，畫面的成功提示不能單獨充當驗收。

### 例 5．Issue 建好了，加入 Project 失敗

- **前提**：尚無「顯示夜間時段」這張卡。合成來源接受建 Issue，指定新識別和顯示編號 #41；首次將該 Issue 加入 Project 時回覆權限不足。
- **操作**：由同一個表單建立並加入 Project，重新開畫面。測試切換為有權限的身分後，只重試「加入 Project」，再重新讀取。
- **結果**：中間畫面可開啟已建立的 #41，顯示「尚未加入 Project」與原因；重試後恰有一張 Issue 和一筆 Project item。以來源資料和請求紀錄確認，建立 Issue 僅送出一次。首次封包已寫入、回應卻遺失的變體，要先釐清操作結果；無法確認時顯示待確認，並保留輸入和查回線索。不得盲目重送建立。

## 交付判斷表

### 例 6．A 做好了，B 還在等驗收

使用第 3 天 16:00 的另一份固定快照。A 為澄河 #11 的查詢成果，必要工作完成且驗收通過；B 為 #12 的匯出成果，必要工作完成但驗收尚未通過。兩者曾共用 WF-31。打開澄河的「交付草案」，先將 B 延到下次，再切換「必須共同生效」，比較同一份證據在兩種條件下的結果。

| 已知相依與目標環境條件 | 本次預期可列為就緒候選 | 應留下的理由 |
| --- | --- | --- |
| A、B 可獨立交付，能選出只含 A 的產物 | A | B 延期，匯出已覆核，仍待驗收 |
| B 需要 A，A 的使用者不需要 B | A | B 留到下一次，屆時再核對目標環境的 A |
| A 需要 B 的能力，目標環境已具相容版本 | A，附該環境相容版本的證據 | 本次 B 的變更仍待驗收 |
| A 需要 B，目標環境沒有相容版本或無法確認 | 無 | 記錄缺少的能力或證據，暫緩 A |
| A、B 必須共同生效，或唯一可用的產物無法安全拆分 | 無 | 兩項一併延後，保留原計畫與阻礙 |

樣稿可操作第一列及最後一列的功能相依情境，部署紀錄維持零筆。產品版若要宣告可交付，還要核對選定成果、必要 workflow、驗收及確切產物；若缺少其中一項，顯示缺件。可依契約選取一張 PBI 的部分成果，明列剩餘條件；保留 PBI 整體的驗收狀態。

### 例 7．一個交付計畫跨環境部署

- **前提**：以合成版本 V3 代表本次 A 的不可變產物，測試環境和正式環境都停在 V2。本次沒有執行任何真實部署。
- **操作**：依序餵入三筆虛構回報：測試環境 V3 成功；正式環境 V3 失敗且目標查回仍為 V2；同一計畫重試後，正式環境 V3 成功並查回 V3。
- **結果**：可從 A 追到一份交付計畫、同一版本與三筆環境結果。第二步後正式環境仍顯示 V2；最後可查到 V3 及前一次失敗的原因。Sprint 結束本身不生成部署。交付前必須完成的 workflow 與執行部署的 workflow 分開記錄，避免把本次部署成功當成本次啟動部署的先決條件。

## 驗收如何執行

| 階段 | 從哪個入口操作 | 查驗證據 |
| --- | --- | --- |
| 現有離線樣稿 | 直接開啟 HTML 手動操作；[瀏覽器檢查頁](github-v1-demo-check.html)走同一組可見的按鈕與清單 | 觀察例 1–3 的導覽、雙向查回、同號隔離，以及例 6 可拆／不可拆的差異。可以重設。這份證據只涵蓋樣稿。 |
| 首個產品切片（01–02） | 使用產品 UI、實際 Board 應用入口與獨立測試儲存，在兩個 session 操作例 1–3 | 第二個 session 依識別讀回最新關聯、原始範圍及交接。只靠瀏覽器暫存無法達成這項驗收。 |
| GitHub 整合與產品 E2E（03–06） | 同一組例 3–5 先以受控 GitHub transport 檢查分頁、拒絕、寫回與重試，再以產品 UI → Board API → adapter → 合成服務跑完整旅程 | 同時比對人看見的結果、來源資料及寫入次數。每次從固定起始資料重建；資料層的期望值直接取自案例表。 |
| 交付增量（07） | 向隔離實例輸入例 6、7 的相依、產物、環境查回事件 | 核對候選清單、延期原因、真正在各環境生效的版本與重試歷史。 |

2026-11-22 的樣稿驗收在 Chrome 通過三組情境。接續的 01、02 已在正式 Web 入口通過本機 Edge E2E：首頁列出兩個產品，WF-31 雖共用仍只出現一次；WF-32 顯示待決事項，補連後關閉第一個瀏覽器工作階段，第二個工作階段從首頁的澄河 #11 讀回關聯、證據及下一步，也能解除關聯並讀回歷史。石庭 #11 可獨立建立 workflow。SQL／HTTP 測試另驗了同版本競爭、回應遺失後原樣重送、權限及來源改名後的建立快照。預覽程序重啟會以新資料庫重建範例。GitHub 寫回與部署結果讀回留給後續切片。

自動操作樣稿時，可於儲存庫根目錄執行下列指令，開啟本機的[樣稿驗收頁](http://127.0.0.1:8000/github-v1-demo-check.html)。伺服器只提供設計目錄。

```powershell
python -B -m http.server 8000 --bind 127.0.0.1 --directory .dev/design/product-evolution
```

如果日後需要證明 GitHub 本身對所選 token、Project 欄位或排序的行為，可另選專用的測試 repository、Project、身分與合成資料，逐筆重新讀回。維持上述三個實際專案的隔離；目前的樣稿與日常 CI 均可獨立運作。
