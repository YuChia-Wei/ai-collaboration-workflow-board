# Requirement presentation guide

Use the caller-selected format and destination. Otherwise, the
[requirement template](requirement-template.md) supplies the single packaged
starting outline; do not maintain another copy here. The
[authoring method](authoring.md) owns source binding, acceptance and uncertainty.

## Naming and organization

A descriptive domain name such as `product-backlog-requirements.md` helps discovery.
Use the target's naming rules and a single coherent document when practical;
multiple linked documents are valid when the selected scope requires them.
Include context/goals, relevant actors, functional requirements, measurable
non-functional targets when known, constraints, business rules, acceptance
criteria and sources only as applicable. Record a missing threshold as open.

## Diagrams

Use a diagram only when it clarifies a flow, state or dependency. Mermaid is a
portable option; a caller-selected diagram format takes precedence. A diagram
must preserve the same source bindings and uncertainty as the prose. It does
not prove implementation or acceptance.

Source-repository requirement instances and historical assessments are not
bundled examples. Populate the outline from the target's actual sources.
