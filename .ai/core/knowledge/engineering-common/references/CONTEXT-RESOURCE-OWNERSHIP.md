# Context Resource Ownership

This method classifies reusable context and project truth. The consuming project
selects its actual paths and adoption policy; this file does not install root
documents, allocate a project record store or authorize writes.

## Single Semantic Owner

- A skill owns its operations and output contract.
- A reusable sub-agent owns a bounded execution role; its presence is not evidence
  of delegation, independence or actual invocation.
- Shared knowledge owns cross-technology engineering semantics. A selected profile
  owns technology-specific defaults and bindings.
- The project owns requirements, decisions, records, applicability, explicit
  technology selections and adopted policies.
- Installed core and runtime entries are managed projections. Examples, indexes,
  analyzers and checklists do not gain semantic authority through repetition.

Separate editable source, installed resources, product documentation and project
records. A reusable package must contain the resources needed by its advertised
capability, or explicitly declare a knowledge dependency. Refer to actual project
facts through caller-selected sources, without requiring the framework author's
private policy filenames. Historical provenance never becomes a live dependency.

## Identity And Strength

Use the [engineering identity contract](ENGINEERING-IDENTITY-CONTRACT.md) and the
selected package's catalog. Stable IDs survive relocation and provider changes.
Missing or ambiguous identities remain unresolved; paths are not substitute IDs.

| Strength | Meaning |
| --- | --- |
| invariant | Preserve adopted engineering meaning; report conflicts. |
| profile-default | Applies when the project adopts that profile; explicit target evidence may replace it. |
| conditional | Applies only when its stated predicate holds. |
| example | Illustrative, without normative force. |
| historical | Provenance, without current execution authority. |

Honor user authority and applicable project instructions. Resolve actual target
facts and declared decision slots before applying an adopted profile. Do not
silently override invariants, imply adoption through installation, or treat a
copied summary as a second normative owner. Technology selection follows the
[portable selection method](TECHNOLOGY-SELECTION-POLICY.md).

## Placement And Progressive Loading

Load the requested capability, then the exact relevant reference. Keep stack
knowledge separate from cross-technology material. A proposed new profile needs
repeated demand, a maintenance owner and observable validation; a sample stack
or folder alone does not establish support.

Maintain human instructions for when to use a capability, required inputs,
expected outputs and limitations separately from agent execution contracts.
Duplicate installation copies are expected; edit source and regenerate only
through an explicitly selected installation operation.

## Evidence Boundary

Discovery tools accelerate selection; direct files, tracked identities and
project-owned checks establish facts. Empty search results do not prove absence.
Record index freshness, scope and exclusions. Runtime declarations and static
profiles do not prove execution. Dependency consistency checks establish
agreement between declarations; they do not establish package currency or
security. Preserve failed, blocked, skipped and deferred results separately.
